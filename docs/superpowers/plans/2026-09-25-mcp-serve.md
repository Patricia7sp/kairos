# Servidor MCP `kairos mcp serve` — stdlib stdio, sem dependência nova

T-24 (`kairos_mcp/server.py`) declara o lado servidor (ferramentas, rationale
de autenticação, ponte de eventos) mas não tem protocolo nem entrada: hoje
`kairos mcp serve` sequer existe no CLI — só `mcp list` é real e
`remove`/`test` recusam 69. Este lote fecha a lacuna com um servidor **stdio
puro em stdlib**, espelhando o protocolo que o cliente `kairos_mcp/runtime.py`
já consome (JSON-RPC 2.0, uma mensagem por linha UTF-8, `2024-11-05`), sem
adicionar o pacote `mcp`.

Origem no legado: `hermes-agent/mcp_serve.py` (usa `mcp.server.MCPServer` +
`run_stdio_async`). Referências de spec: `_reversa_sdd/mcp/` §9 (Tarefa 12).

## Contrato

`kairos mcp serve` sobe em primeiro plano, lê requisições do stdin, escreve
repostas no stdout (nada além de JSON-RPC mangueia o stdout), encerra 0 no EOF
do stdin. Um cliente MCP qualquer (editor, desktop) que spawne o processo
conversa com as conversas do Kairos: `initialize` → `notifications/initialized`
→ `tools/list` → `tools/call`. Requisição desconhecida responde `-32601`;
notificação é descartada; JSON inválido responde `-32700`.

Ferramentas publicadas (dono real, nunca sucesso inventado):

1. `conversations_list(limit, search, platform)` — sessões `hidden=0` da
   `state.db`, ordem por `last_activity_at`/`started_at`; busca textual como a
   tela web (`display_name`/`title`/`id`/`source`/`model`/mensagem); filtro
   `platform` lê `origin_json.platform`/`chat_type` quando a sessão registrou
   (nada popula hoje → filtro devolve lista vazia, que é o estado real).
2. `conversation_read(session_key, limit)` — transcrição em ordem, papéis
   user/assistant, `content[:2000]`.
3. `session_info(session_key)` — linha completa da sessão, seleção de modelo
   (provider/model/reason), contagens, custo, tags.
4. `conversation_search(term, limit)` — `SearchIndex` (FTS5→trigram→CJK→LIKE),
   com a sessão e o contexto de cada ocorrência.
5. `events_poll(after_cursor, session_key, limit)` — `EventBridge` com
   baseline por sessão no start (sessão nova emite desde a primeira mensagem);
   cursor = id global de mensagem.
6. `messages_send(target, message)` — envia **agora** via adapter e **grava a
   obrigação no ledger durável** (mesmo caminho de
   `kairos_web/messaging_api.py`): `record` → `claim` → adapter → `confirm` /
   `release` / `abandon`. Plataforma não entregável é **recusa honesta**, não
   entrega fingida. Nenhum efeito sem rastro.
7. `platforms_list()` — `messaging_status(home)`: entregáveis, obrigações no
   ledger e estado por plataforma, sem segredo.

## Divergências deliberadas do Kairos (D-MCP.11)

- **`attachments_list` deixa de ser publicada.** No legado, extraía blocos
  não-textuais das mensagens; no Kairos nada persiste anexo — o inbound não
  armazena mídia e `messages` guarda só conteúdo textual. Publicar a
  ferramenta seria "reportar sucesso sem efeito" (sempre `0 anexos`). Vai para
  `UNPUBLISHED_TOOLS` com o motivo, mesmo padrão das `permissions_*`.
- **Servidor stdlib, sem o pacote `mcp`.** O legado dependia do servidor do
  pacote; o Kairos o trata como opcional no cliente. Um servidor stdio é
  poucas centenas de linhas de JSON-RPC — e manter a dependência fora
  preserva a leveza da imagem e a simetria com o cliente.
- **Envio direto, sem long-poll.** `events_poll` é pull com cursor, como o
  legado; `events_wait` (long-poll) não é portado — custaria um thread de
  espera dentro do servidor stdio para um consumidor que não o usa.
- **Autenticação permanece ausente e escrita** (`AUTHENTICATION_RATIONALE`):
  transporte stdio, fronteira = OS; transporte remoto futuro exige rever a
  decisão antes de existir.

## Implementação

1. `kairos_mcp/serve.py` — `MCP_PROTOCOL_VERSION` (reuso do runtime),
   `ToolError`, o `MCPServer` (home, `connect`+`migrate` no start, baseline do
   `EventBridge` por `SELECT session_id, MAX(id) FROM messages GROUP BY
   session_id`, repos `SessionRepository`/`SearchIndex`/`LedgerRepository`) e
   `serve_stdio(home)` — laço `readline` em `sys.stdin.buffer`, resposta JSON
   por linha, códigos de erro JSON-RPC, EOF → 0.
2. `kairos_mcp/server.py` — move `attachments_list` de `SERVER_TOOLS` para
   `UNPUBLISHED_TOOLS` com o motivo (D-MCP.11).
3. `kairos_cli/commands.py` — subcomando `serve` em `mcp`.
4. `kairos_cli/handlers.py` — `cmd_mcp` trata `mcp serve` chamando
   `serve_stdio(_home())`; nada imprime no stdout além do JSON-RPC.
5. Testes de comportamento (não snapshot): `tests/test_mcp_serve.py`
   — unit para coerção de parâmetros e catálogo; integração em subprocesso
   **real** (`kairos mcp serve` com `KAIROS_HOME` descartável): handshake
   `initialize`, `tools/list` (as 7, sem `attachments_list`), listar/ler/buscar
   conversas em banco semeado, **baseline do `EventBridge`** (sessão pré-start
   não reemite; sessão criada após o start emite desde a primeira mensagem),
   `messages_send` para plataforma não entregável devolve `isError` honesto,
   método desconhecido responde `-32601`, EOF encerra 0. Família e CLI surface
   do GNUv1: `mcp serve` deixa de recusar 69.
6. Registrar D-MCP.11 em `docs/decisoes.md`, progresso em
   `docs/functional-progress.md`. Suíte completa + `ruff`/`format` +
   `ci.sh --fast`.

## Fora de escopo

- Não publica `permissions_*` nem cria IPC de aprovação (exige o gateway).
- Não adiciona o pacote `mcp`; o cliente continua no-op sem ele.
- Não cria storage novo (sem tabela de anexos, sem fila própria).
- Não altera o toolset do modelo (`kairos_tools/mcp_tools.py` fica intacto).
